# Deployment

Two environments, one set of machinery (Phase 21):

- **Production**: a long-lived AWS Lightsail instance,
  `zainstreat-production` (Amazon Linux 2023, 4 GB RAM, `eu-central-1`,
  static IP `63.185.172.26`), serving
  `zainstreat.com`, `cms.zainstreat.com` (admin), `api.zainstreat.com` and
  `logs.zainstreat.com`.
- **Staging**: an *ephemeral* Lightsail instance (2 GB) created and deleted
  on demand, served on `<ip-with-dashes>.sslip.io` (plus `cms.`, `api.`,
  `logs.`) with real HTTPS and no custom domain. Lightsail bills a stopped
  instance in full, so staging is deleted, not stopped, when unused.

Images are built on GitHub's runners and pushed to private GHCR packages,
tagged by commit SHA. Servers never build anything, and their `.env` is
generated by the deploy — never edited by hand.

All routine work is a GitHub Actions workflow (repo → **Actions**). SSH
is for emergencies only (see the end of this document).

## Release flow

1. Merge to `master`. **CI** (`ci.yml`) runs API tests, web lint and build.
2. **Build** (`build.yml`) then builds `zainstreat-api:<sha>` and
   `zainstreat-web:<sha>` (with `DOMAIN` baked in, Phase 19). If staging
   is up, it also builds `zainstreat-web-staging:<sha>` for staging's
   domain and deploys staging.
3. Check staging, then run **Promote** (`promote.yml`) from `master`,
   leaving `sha` **empty** to ship the latest `master` commit. It checks
   the images exist and that `cms.zainstreat.com` resolves, then waits
   for a reviewer to approve the `production` Environment before
   deploying. It never rebuilds. If Build hasn't finished for the newest
   commit yet, Promote says the image doesn't exist; wait and re-run.

**Rollback** is **Promote** with an earlier full 40-character SHA. Repo → **Deployments** →
`production` lists what ran when.

Every deploy goes through `_deploy.yml`, which:

- renders `.env.next` from the target Environment's secrets/variables
  (every value single-quoted, so `$` is literal);
- uploads it with the compose files, `Caddyfile`, and the
  `infra/backup-stream.sh` / `infra/env-parity.sh` helpers;
- runs the **env parity preflight**: resolves the live `.env` and
  `.env.next` through compose on the server and prints the *names* of
  keys whose values differ (never the values). On production, any
  difference not listed in Promote's `allow_env_changes` input fails the
  deploy before anything changes; on staging it only reports;
- pulls with a short-lived token (`docker login` → pull → `docker
  logout`), `up -d`, restarts Caddy, prunes superseded images;
- fails unless `https://api.<domain>/health`, `https://<domain>/en` and
  `https://cms.<domain>/login` answer within 5 minutes.

### Changing a secret or setting

Edit it on the Environment (repo → Settings → Environments), then
Promote the currently deployed SHA with `allow_env_changes` set to the
key(s) you changed (e.g. `RUST_LOG`). For a credential such as
`POSTGRES_PASSWORD`, changing the secret does **not** change the
database's password — only do that as part of a deliberate rotation.

## Staging

- **Up:** run **Staging up** (optionally with a built SHA; default is the
  branch you run it from). It creates `zainstreat-staging` from
  `infra/bootstrap.sh` if it doesn't exist, opens 22/80/443, builds the
  staging web image, deploys, loads `apps/api/seed.sql`, and creates the
  admin from the staging Environment's `ADMIN_EMAIL`/`ADMIN_PASSWORD`.
  The run summary lists the URLs. Re-running while it's up redeploys in
  place.
- **Down:** run **Staging down** and type `DELETE STAGING`. Data goes
  with it. The workflow (and the IAM role) only delete an instance tagged
  `env=staging`.
- Staging sends `X-Robots-Tag: noindex` everywhere. It notifies
  `contact@zainstreat.com` like production, but its
  `EMAIL_SUBJECT_PREFIX` (`[STAGING] `) tags every subject (Phase 25).
- If sslip.io is down, set the `STAGING_DNS_SUFFIX` repository variable to
  `nip.io` and run Staging up again.

## Admin accounts

Run **Create admin**: pick the environment, enter the email and name. The
password comes from that Environment's `ADMIN_PASSWORD` secret — never a
workflow input, which would be visible on the run page. For production:
set the secret, run the workflow, then delete the secret. An existing
admin with the same email gets the new password.

Locally, the dev `api` container only runs `cargo run --bin api`, so run
the binary through cargo:

```bash
docker compose exec api cargo run --bin create_admin -- --email owner@zainstreat.com --name "Zain"
# or non-interactively:
printf '%s\n' "$PASSWORD" | docker compose exec -T api cargo run --bin create_admin -- --email owner@zainstreat.com --password-stdin
```

## Backups and restore

- **Backup** runs nightly at 02:30 UTC for production, and on demand for
  either environment. The runner streams a `pg_dump -Fc` and a MinIO data
  archive over SSH using a dedicated **backup key** whose
  `authorized_keys` forced command (`/opt/zainstreat/bin/backup-stream`)
  can do nothing else, and uploads them to
  `s3://<BACKUP_BUCKET>/<env>/<timestamp>/` (expires after 30 days). The
  server holds no AWS credentials. The nightly job uses the
  `production-backup` Environment, which has no reviewer and holds only
  the backup key.
- **Restore** takes an environment, a prefix as printed by Backup (e.g.
  `production/20261101T023000Z`) and the phrase `RESTORE <environment>`.
  Restoring into production waits for reviewer approval and takes a
  fresh `…-pre-restore` backup first. Restoring a production backup into
  staging is a good way to rehearse, or to test against real data.
- Lightsail's automatic daily instance snapshots stay enabled on
  production as a second, whole-box layer.

## Seeding the production menu

`apps/api/seed.sql` **replaces** all categories, menu items and price
options (`TRUNCATE ... CASCADE`). Since Phase 14 the menu is edited in
the admin, so this is rarely wanted. Run **Seed Production Database** and
type `SEED PRODUCTION`; it `pg_dump`s to
`/opt/zainstreat/backups/backup-<timestamp>.sql` on the server first, then
seeds and prints row counts. To undo, use **Restore** with the latest S3
backup.

## Viewing logs

**Dozzle** at `https://logs.<domain>` (HTTP Basic Auth:
`DOZZLE_BASIC_AUTH_USER` / `DOZZLE_BASIC_AUTH_HASH` on the Environment;
generate the hash with `docker run --rm caddy:2-alpine caddy
hash-password` and store it exactly as printed). It tails every
container, which is why it's gated. `RUST_LOG`/`LOG_FORMAT` are
Environment variables; change them as described under "Changing a secret
or setting".

## One-time setup

What has to exist before the workflows work. Full detail is in
`specs/2026-10-31-phase-21-pipeline-refactor/plan.md` Groups 1–2.

- **AWS (once per account):** the GitHub OIDC identity provider; IAM role
  `zainstreat-github-actions` (trusts only this repo, by GitHub's
  immutable `repo:<owner>@<id>/<repo>@<id>` subject; Lightsail
  read/create plus delete/firewall changes limited to `env=staging`; S3
  on the backup bucket only); the private backup bucket with a 30-day
  expiry rule.
- **Repository variables:** `AWS_ROLE_ARN`, `AWS_REGION`, `BACKUP_BUCKET`,
  `DOMAIN`, `PROD_DEPLOY_HOST`, `STAGING_DNS_SUFFIX`.
- **Environments:** `staging`, `production` (required reviewer, `master`
  only) and `production-backup` (`master` only), each with the secrets and
  variables listed in `.env.example`, plus `DEPLOY_SSH_KEY`,
  `BACKUP_SSH_KEY`/`BACKUP_SSH_PUBLIC_KEY`, and (staging)
  `DEPLOY_SSH_PUBLIC_KEY` and `ADMIN_*`.
- **GHCR packages** `zainstreat-api`, `zainstreat-web` and
  `zainstreat-web-staging` are **private**, with the `zainstreat` repo
  listed under "Manage Actions access".
- **DNS** at the domain's existing provider: A records for `@`, `www`,
  `cms`, `api` and `logs` → the production static IP, plus the SES DKIM
  records.
- **Off-box monitoring** (Phase 18): Lightsail alarms (CPU ≥ 70%, burst
  capacity ≤ 20%, status-check failures) emailed to the owner, and an
  external uptime monitor on `https://zainstreat.com/en` and
  `https://api.zainstreat.com/health`.

### Building a new server

For disaster recovery or the move to the client's AWS account (Phase 29):
create a Lightsail instance (Amazon Linux 2023, 4 GB) with
`infra/bootstrap.sh` as its launch script — replace
`__DEPLOY_SSH_PUBLIC_KEY__` with the production deploy public key first —
attach the static IP, open 22/80/443, and enable automatic snapshots.
Then run **Promote** with the current SHA (a fresh box has no `.env`, so
the parity check is skipped), and **Restore** the latest production
backup. The script installs Docker + Compose, a 2 GB swap file
(`vm.swappiness=10`), a persistent systemd journal, the sudo-less
`deploy` user, and `/opt/zainstreat`; its log is
`/var/log/zainstreat-bootstrap.log`.

Every container in `docker-compose.prod.yml` has a `mem_limit` (with
`memswap_limit` equal to it) and a `cpus` ceiling sized for the 4 GB box,
so one runaway service gets OOM-killed and restarted instead of hanging
the host. The dev compose file stays unlimited.

## Email (Amazon SES)

Order confirmations and business notifications (Phase 17) go out through
SES SMTP; without credentials the API logs every send as a no-op.

1. Verify the sending domain (SES → Identities → Create identity) and add
   its DNS records.
2. Create SMTP credentials (SES → SMTP settings) — distinct from IAM
   keys.
3. Request production access (SES → Account dashboard) to leave the
   sandbox.
4. Set `SES_SMTP_HOST`, `SES_SMTP_USERNAME`, `SES_SMTP_PASSWORD`,
   `EMAIL_FROM_ADDRESS` and `EMAIL_BUSINESS_NOTIFY_ADDRESS` on the
   Environment, then Promote (see "Changing a secret or setting").
   `EMAIL_FROM_ADDRESS` is a bare address. The API adds the display name
   "Zain's Treat n More" itself (Phase 24), because the deploy rejects a
   `'` in env values. The optional `EMAIL_SUBJECT_PREFIX` goes in front of
   every subject (`[STAGING] ` on staging, unset on production).

### `contact@zainstreat.com` (Phase 25)

- **Sending.** `contact@` is both `EMAIL_FROM_ADDRESS` and
  `EMAIL_BUSINESS_NOTIFY_ADDRESS` on staging and production. The verified
  `zainstreat.com` SES domain identity covers it, so no extra identity is
  needed.
- **Reply-To.** Customer emails (invoice, status update, quote) reply to
  `contact@`. Owner notifications (new order, payment claimed, quote
  accepted/declined, catering enquiry, contact message) reply to the
  customer, so the owner can answer straight from the notification.
- **Receiving.** The domain's DNS is a **Lightsail DNS zone**
  (Lightsail → Domains & DNS) in the same AWS account as SES and the
  servers. Namecheap is only the registrar. Its `awsdns` nameservers look
  like Route 53, but there's no Route 53 hosted zone. Inbound mail is
  forwarded by **ImprovMX** (free plan):
  - Apex records: `MX 10 mx1.improvmx.com`, `MX 20 mx2.improvmx.com`
    (in the Lightsail console the priority is its own field), and the
    only SPF TXT record
    `v=spf1 include:spf.improvmx.com include:amazonses.com ~all`.
    DMARC stays `p=none`. SES's DKIM signature survives forwarding, so
    forwarded notifications pass DMARC.
  - The ImprovMX alias `contact` forwards to the developer's inbox for
    now. **Before production launch**, change the alias target to the
    owner's inbox in the ImprovMX dashboard. It's a dashboard edit, with
    no code or DNS change.
- **Failed customer emails.** Each customer email is recorded in
  `email_deliveries` (`queued` → `sent`/`failed`). If the latest one for
  an order or quote failed, or is still unconfirmed after 5 minutes, the
  admin order or enquiry page shows "Customer email may not have been
  delivered" next to the WhatsApp and copy-link buttons. While SES is in
  the sandbox, any unverified recipient fails this way.

## Editing the site (Phase 25)

- **Site content** (`cms.<host>/site`): the logo, eight site images and the
  homepage text in English, Dutch and French. An empty text field or a
  "Reset to default" image falls back to the bundled default.
- **Drafts.** Site content, menu item and category edits autosave as a
  draft about a second after typing stops. The public site and ordering
  only ever see published data. New items and categories start
  **Unpublished**. Availability and archive still take effect at once.
- **Publish.** Each editor has "Publish this change" and "Discard draft".
  `cms.<host>/changes` lists everything pending, with a before/after diff,
  and **Publish all** applies it in one step. If anything changed since the
  page loaded, nothing is published and the page asks for a reload.
- **Live preview.** Editors show the real public page with the draft
  applied in a device simulator (Mobile S 320px to Desktop XL 1920px, one
  device or all at once). `cms.<host>/preview-all` is the full-screen
  version. It uses Next.js draft mode on the cms host only. If a frame
  says "Preview couldn't start here", log in again or use "Open in a new
  tab".

## Resizing the production instance

Lightsail can't resize in place; a resize is a snapshot restore onto a
bigger plan, which also tests the snapshots:

1. **Stop** the old instance, then **Create snapshot** and wait for
   *Available*.
2. From the snapshot → **Create new instance**, same region/AZ, bigger
   plan.
3. On the new instance, check the firewall is exactly `22`/`80`/`443`
   (IPv4 and IPv6) and re-enable **Automatic snapshots**; recreate the
   Lightsail alarms (they're per instance).
4. Move the static IP from the old instance to the new one. DNS and
   `DEPLOY_HOST` don't change.
5. Run **Promote** with the current SHA and check `https://cms.<domain>`
   orders (Postgres) and the live menu photos (MinIO).
6. Keep the old instance **stopped, not deleted**, for 7 days; rollback is
   moving the static IP back.

## Emergency-only SSH

Everything above works without SSH. These are the cases that still need
it, using the **admin** key (`ec2-user`, sudo) — or Lightsail's
browser-based SSH from the console if that key isn't to hand.
`/opt/zainstreat` is owned `deploy:deploy` (`rwxr-x---`), so prefix
commands there with `sudo`.

### When the site is down

Written after the 2026-10-11 outage, where nothing answered and no
evidence survived the reboot.

1. **Confirm from off-box:** the uptime monitor, and Lightsail →
   instance → **Metrics** (CPU utilization *and* burst capacity; burst at
   0% means CPU-credit exhaustion, moderate CPU with everything
   unresponsive usually means memory pressure). Screenshot both.
2. **Reboot** from the Lightsail console. If it isn't back in ~5 minutes,
   **Stop** then **Start** (keeps the static IP and disk).
3. **Capture evidence** as soon as SSH works:
   ```bash
   uptime; free -m; swapon --show; df -h /
   sudo journalctl -k -b -1 --no-pager | grep -iE "out of memory|oom|killed process|hung_task|blocked for more than" | tail -40
   sudo journalctl --list-boots | tail -5
   sudo -i
   cd /opt/zainstreat
   C="docker compose -f docker-compose.yml -f docker-compose.prod.yml"
   $C ps -a; docker stats --no-stream; docker system df
   $C logs --since 6h caddy | grep -o '"uri":"[^"]*"' | sort | uniq -c | sort -rn | head -25
   $C logs --since 6h caddy | grep -o '"User-Agent":\["[^"]*"' | sort | uniq -c | sort -rn | head -15
   $C logs --since 6h web | tail -100
   ```
4. **Record findings** (cause: memory / disk / burst credits / crawler /
   other). If a `mem_limit` is too low for normal traffic, raise it in
   `docker-compose.prod.yml` and ship it through the normal release flow.

### If the deploy pipeline itself is broken

Promote can't run (GitHub outage, broken workflow): SSH in, `sudo -i`,
`cd /opt/zainstreat`, and set `API_IMAGE`/`WEB_IMAGE` in `.env` to a known
good `…:<sha>`, then `docker compose -f docker-compose.yml -f
docker-compose.prod.yml up -d`. Images that aren't already on the box need
`docker login ghcr.io` first (a personal token with `read:packages`;
`docker logout ghcr.io` afterwards). The next Promote overwrites `.env`
again.
